## Overview

[Portabase Agent](https://portabase.io/) is a background service that connects database servers to Portabase and executes backup and restore tasks configured through the Portabase Dashboard.

The agent is intended to run close to the databases it manages. It periodically contacts the Dashboard to check for tasks; the Dashboard does not need to initiate an inbound connection to the agent. This means the agent does not need a public web interface or an incoming port mapping for its normal operation.

This repository provides an Unraid Community Applications template for the upstream `portabase/agent` Docker image. The Agent is one component of the Portabase platform; you also need a Portabase Dashboard that is reachable from the agent.

> **This is an agent, not the Portabase Dashboard.** It runs in the background and has no standalone WebUI.

### At a glance

| Setting | Value in this repository's template |
|---|---|
| Docker image | `portabase/agent:latest` |
| Container type | Background service |
| Web interface | None |
| Published ports | None required |
| Default Docker network | `bridge` |
| Required credential | `EDGE_KEY` generated by the Portabase Dashboard |
| Timezone | `Europe/Paris` |
| Polling interval | `5` seconds |
| Persistent data | `/mnt/user/appdata/portabase/agent/data` → `/data` |
| Optional configuration directory | `/mnt/user/appdata/portabase/agent/config` → `/config` |
| Upstream license | Apache-2.0 |

## How Portabase Agent works

Portabase separates the central management interface from the agents that perform database operations.

1. Install or access a Portabase Dashboard.
2. Create an agent in the Dashboard and copy its **Edge Key**.
3. Install Portabase Agent on the Unraid server where the target databases are reachable.
4. Configure the agent using the Edge Key.
5. The agent periodically contacts the Dashboard and receives assigned tasks.
6. The agent performs the configured backup or restore operation and reports its status.

The agent can work with existing databases or, depending on the database type and configuration, databases deployed in Docker. The Dashboard is used to manage agents, database connections, backup jobs, storage destinations and notifications.

### Supported database types

The current Portabase documentation lists support for database types including:

- PostgreSQL
- MySQL and MariaDB
- MongoDB
- SQLite
- Firebird
- Microsoft SQL Server
- Redis and Valkey (backup support; restore support may differ)
- Docker named volumes
- Files and directories, depending on the installed Agent version

Check the [official supported-databases documentation](https://portabase.io/docs) for current engine support, restore capabilities, version requirements and engine-specific options.

## Install on Unraid

1. Open **Apps** in the Unraid web interface.
2. Search for **Portabase Agent**.
3. Select the template provided by **MikaPST — Unraid Community Apps** and click **Install**.
4. In the `EDGE_KEY` field, enter the Edge Key generated by your Portabase Dashboard. This field is treated as a secret in the Unraid template.
5. Review the timezone, polling interval and persistent directory mappings.
6. Click **Apply** and wait for the container to start.

There is no URL to open for the agent itself. Once connected, the agent should appear in the Portabase Dashboard.

### What the template configures

The template documented by this repository configures:

- The upstream `portabase/agent:latest` Docker image
- The `bridge` network by default
- The required `EDGE_KEY` variable
- Timezone configuration (`Europe/Paris` by default)
- A configurable polling interval (5 seconds by default)
- A persistent agent data directory
- An optional configuration directory
- No published web port and no WebUI

A Portabase Dashboard must already be available, and the agent must be able to reach the Dashboard URL encoded in the Edge Key.

## Connect the agent to Portabase

### 1. Create an agent in the Dashboard

Open your Portabase Dashboard and create a new Agent. Copy its **Edge Key**.

Treat the Edge Key as a password. It contains connection information and credentials used to associate the agent with your Portabase installation.

### 2. Enter the Edge Key in Unraid

During installation or when editing the existing container:

1. Locate the `EDGE_KEY` variable.
2. Paste the key copied from the Dashboard.
3. Apply the configuration to recreate the container with the updated setting.
4. Check the container logs if the agent does not appear as connected.

Do not paste your real Edge Key into a public issue, GitHub commit, screenshot or shared log.

### 3. Confirm the connection

Open the Portabase Dashboard and check the agent list. The agent should appear as connected after it starts communicating with the Dashboard.

If it does not connect, verify that:

- The Edge Key was copied completely and belongs to the intended agent.
- The Dashboard URL referenced by the key is reachable from Unraid.
- DNS resolution and outbound HTTPS/network access are working.
- The container logs do not show connection, authentication or configuration errors.

## Configuration reference

The template exposes a small set of settings for common Unraid deployments.

### Template settings

| Setting / variable | Default in this template | Description |
|---|---|---|
| `EDGE_KEY` | Required | Unique key generated by the Portabase Dashboard; the value is masked |
| `TZ` | `Europe/Paris` | Timezone used by the agent |
| `POLLING` | `5` | Interval between checks for new tasks, in seconds |
| Agent Data | `/mnt/user/appdata/portabase/agent/data` → `/data` | Persistent directory for agent data |
| Agent Configuration | `/mnt/user/appdata/portabase/agent/config` → `/config` | Optional directory for local agent configuration |

The values above describe the Unraid template in this repository. They may differ from the defaults used by a manual Docker deployment or a newer upstream version.

### `EDGE_KEY`

`EDGE_KEY` is required. Generate it in the Portabase Dashboard when creating an Agent.

- Do not reuse a key from a different agent unless the Dashboard specifically instructs you to.
- Do not commit a real key to version control.
- If a key is exposed, revoke or replace it from the Portabase side as appropriate and update the Unraid container.

### `TZ`

The template uses:

```text
Europe/Paris
```

Change it if you want the agent to use another timezone. The official Agent documentation currently lists `UTC` as the upstream default when no timezone is supplied.

### `POLLING`

The template defaults to:

```text
5
```

The value is in seconds. It controls how often the agent checks for tasks. A higher interval may reduce polling frequency but can increase the delay before a newly assigned task is noticed. Check the upstream documentation before setting a value unsupported by your installed version.

### Persistent data and configuration

The data directory is mapped as follows:

```text
/mnt/user/appdata/portabase/agent/data  →  /data
```

The template also provides an optional configuration directory:

```text
/mnt/user/appdata/portabase/agent/config  →  /config
```

Keep persistent mappings in place if your setup stores data or configuration files there. Whether you need local database configuration files depends on how you configure the agent and which features you use; database definitions managed from the Dashboard may not require the same local files as a manually configured deployment.

For the current file formats and environment variables, see the [official Agent environment-variable reference](https://portabase.io/docs/agent/environment).

## Connect databases

A connected agent must be able to reach every database server it is responsible for backing up or restoring.

Portabase supports both existing database servers and selected database types that can be deployed through Docker. The exact configuration depends on the engine, authentication method and whether the database runs on Unraid, in another container or on a remote server.

### Databases in other Docker containers

If a database runs in another container, make sure the agent can resolve and reach it.

Common approaches include:

- Connecting the Agent to a shared user-defined Docker network with the database container, then using the database container's Docker DNS name and internal port.
- Connecting to a host-reachable address and a port published by the database container.
- Using an address and port for a database on another machine.

The template uses Docker's `bridge` network by default. Containers on the default bridge network do not automatically receive the same service-name discovery behaviour as containers attached to the same user-defined bridge network. Adapt the network configuration to your environment.

### Least-privilege database credentials

Use dedicated database credentials with only the permissions necessary for the backup and restore operations you plan to perform. Requirements differ by database engine and by the type of dump or restore operation.

Before relying on a setup for production data:

1. Complete a backup and confirm that it is recorded successfully in Portabase.
2. Test a restore against a separate test database or environment.
3. Verify the restored data and application behaviour.
4. Document any engine-specific permissions or limitations.

Never expose a database service publicly simply to make it reachable by the Agent. Use private networks, VPNs or firewall rules instead.

## Networking

Portabase Agent is designed to make outbound connections to the Dashboard. In a standard deployment, it does not need a port published to the Unraid host.

### Required network access

The agent needs to reach:

1. The Portabase Dashboard URL associated with its Edge Key, usually over HTTPS.
2. Each database server configured for backup or restore.
3. Any required storage or external service endpoints, where the Agent's configured task requires them.

The Dashboard does not normally initiate inbound connections to the Agent. This reduces the need to expose the database environment to incoming connections from the Dashboard.

### Choosing a Docker network

The template uses `bridge` by default. You may need to change the network if:

- Your databases are attached to a custom Docker network.
- Your infrastructure uses separate networks for management and databases.
- You want to resolve a database container by its service/container name.

If you attach the Agent to a custom network, ensure it can still reach the Dashboard and that the change follows your local segmentation policy.

## Back up Docker volumes

Portabase supports Docker named-volume backups through a dedicated database type. This feature differs from a logical database backup: it archives the contents of a Docker volume directly.

**Important:** Docker-volume backup requires access to the Docker socket. The standard Agent template described in this repository does not list the Docker socket as a default mount, so this feature may not work unless you deliberately add and configure that access.

The required mount is typically:

```text
/var/run/docker.sock:/var/run/docker.sock
```

Only add this mount if you need Docker-volume operations and understand the security implications. Access to the Docker socket can grant powerful control over the Docker host.

### Temporary storage requirements

For Docker-volume backups and restores, the Agent may build temporary archives inside the container. Large volumes can require substantial temporary free space.

The official documentation notes that `TMPDIR` can be set to a directory with sufficient space. For example, you could mount a larger Unraid directory into the container and configure `TMPDIR` to point to it. Do not add such a mapping without checking the paths and environment variables supported by your installed Agent version.

See the [official Docker Volume documentation](https://portabase.io/docs/agent/db/docker-volume) for the current setup and storage requirements.

## Security recommendations

- **Keep `EDGE_KEY` secret.** Do not publish it in a template, repository, screenshot or unredacted log.
- **Do not publish an Agent web port.** The Agent has no WebUI and does not require an incoming port for normal operation.
- **Restrict database connectivity.** Allow the Agent to reach only the database servers and ports it needs.
- **Use least-privilege database accounts.** Select permissions based on the actual backup and restore operations required.
- **Protect Docker socket access.** Do not mount `/var/run/docker.sock` unless you need features that require it, such as Docker named-volume backups.
- **Protect backup destinations.** Apply access control, encryption and retention policies to stored backups.
- **Test restores.** A successful backup run is not a substitute for a verified restore procedure.
- **Keep the image updated.** Review upstream releases and changes before upgrading production installations.

The official Portabase project describes encrypted backups and multiple storage backends, but the effective security of a deployment also depends on how the Dashboard, Agent, credentials, networks and storage are configured.

## Troubleshooting

### The agent does not appear in the Dashboard

- Verify that the container is running.
- Confirm the Edge Key is correct and belongs to the agent you created.
- Check that the Dashboard URL is reachable from the Unraid server.
- Review the container logs for connection or authentication errors.

### The agent connects, but no database task succeeds

- Verify the database host, port and credentials configured in Portabase.
- Confirm the Agent can resolve and reach the database from its Docker network.
- Review the database engine's permission requirements for the selected backup or restore method.
- Check the Agent logs and the task details in the Dashboard.

### The Agent cannot reach a database container by name

- Confirm the Agent and database are connected to a suitable shared user-defined Docker network.
- Verify the internal database port and container DNS name.
- If using the default `bridge` network, consider a custom network or a suitable host-reachable address.

### Docker-volume backup fails

- Confirm that the Agent has the required Docker socket mount.
- Check that the named volume exists and that the Agent can inspect it.
- Verify that the temporary directory has enough free space for the backup or restore archive.
- Consult the [Docker Volume documentation](https://portabase.io/docs/agent/db/docker-volume) for feature-specific requirements.

### The Agent's time or task polling seems wrong

- Verify the `TZ` value.
- Confirm that `POLLING` is expressed in seconds.
- Review container logs and the current upstream environment-variable documentation.
